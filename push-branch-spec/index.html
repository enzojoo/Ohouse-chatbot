개요

목적

  • 고객센터 새 답변 알림 발송 시, 발송 직전에 Braze로 앱 푸시 수신 가능 여부를 조회하고 결과에 따라 앱 푸시와 LMS로 채널을 분기하는 구조를 정의

적용 범위

  • 알림 2종 — 채팅 새 답변 알림 / 1:1 문의 새 답변 알림
  • 발송 주체는 AICX이며, 오늘의집은 Braze 캠페인, API 키, LMS 템플릿, 딥링크 규격을 제공

현황

기존 발송 구조

  • As-is는 새 답변 발생 시 Braze 앱 푸시를 단건 발송하는 구조이며, 수신이 불가한 유저는 알림을 전혀 받지 못함
  • 실측 결과 전체 인입 중 앱 푸시 도달 가능 비중은 55.1% 수준 (2026-07-27 ~ 2026-08-22, 채팅 + 1:1 문의 12,796건 기준)
구분비중
앱 푸시로 커버55.1%
회원이지만 푸시 불가 — LMS 대상30.2%
비회원 — 알림 수단 없음14.7%

수신 가능 여부 판정 구조

  • Braze에는 발송 건별 수신 여부를 조회하는 API가 없음
  • 따라서 발송 전에 수신 가능 여부를 판정해 채널을 분기하는 구조로 구현 필요

지연 시간 실측

사내망에서 iad-03 호출 기준 3회 안정값

단계현재 — 앱 푸시만 발송변경안 — 사전 판정 후 분기
수신 가능 여부 조회없음0.32초 (50건 배치 시 0.61초)
분기 판정없음코드 내 처리
발송 호출0.24초앱 푸시 0.24초 / 불가 시 LMS 발송 호출
합계약 0.24초약 0.56초

연동 스펙

공통

항목값
호스트https://rest.iad-03.braze.com (오늘의집 인스턴스 = dashboard-03)
인증 헤더Authorization: Bearer {REST API 키}
Content-Typeapplication/json
유저 식별자external_user_id = 오늘의집 회원번호 / 반드시 문자열로 전송 (숫자로 보내면 매칭 실패)

1단계 — 수신 가능 여부 조회

요청 POST /users/export/ids

{
  "external_ids": ["12345678"],
  "fields_to_export": ["external_id", "push_subscribe", "push_tokens"]
}

응답 예시

{
  "users": [{
    "external_id": "12345678",
    "push_subscribe": "opted_in",
    "push_tokens": [
      { "app": "오늘의집", "platform": "iOS", "notifications_enabled": true }
    ]
  }],
  "invalid_user_ids": [],
  "message": "success"
}
  • fields_to_export는 위 3개로 고정할 것 — 필드를 좁히면 rate limit이 초당 40건으로 확보되나, campaigns_received를 포함하면 분당 250건으로 떨어짐
  • external_ids는 요청당 최대 50건
  • 알림은 건별로 발생하므로 1건 조회가 기본이며, 배치 재알림 등에서만 묶어서 호출

2단계 — 판정 규칙

위에서부터 순서대로 확인하고, 먼저 걸리는 조건으로 확정

순서확인 항목조건판정
1invalid_user_ids회원번호가 여기에 포함됨 (Braze 프로필 없음)앱 푸시 불가 → LMS
2push_subscribe값이 unsubscribed앱 푸시 불가 → LMS
3push_tokens배열이 비어 있음 (등록 기기 없음)앱 푸시 불가 → LMS
4notifications_enabledtrue인 토큰이 하나도 없음앱 푸시 불가 → LMS
5-1~4에 모두 해당하지 않음앱 푸시 발송
4번 조건을 빠뜨리면 대상자의 절반가량을 오판함. push_subscribe와 push_tokens만 보면 토큰은 있으나 기기 알림이 꺼진 유저가 발송 가능으로 잡힘
  • notifications_enabled는 Braze 문서상 포그라운드 푸시 관련 필드로 기술되어 있으나, 표본 450명 교차검증에서 오늘의집 기기 알림 동의 값과 일치하는 것이 확인되어 판정에 사용
  • 회원당 등록 기기는 평균 2개, 최대 15개 (무효 토큰 누적) — 토큰 배열은 항상 다건 전제로 처리할 것

3-A단계 — 앱 푸시 발송

  • 기 전달되었던 API를 활용하여 앱 푸시 발송

3-B단계 — LMS 발송

  • 콜봇 셀프서비스 문자에서 사용 중인 NHN Cloud SMS API v2.2 경로를 그대로 재사용
    • 발신번호 1670-0876
    • 알림 2종용 LMS 템플릿은 미등록 상태이며, 문안 확정 후 오늘의집에서 등록
    • 회원 전화번호 조회 경로는 미확정 — AICX 보유 데이터로 커버되는지 확인 필요

딥링크 규격

발송 채널별로 링크 형식이 다름. 앱 푸시는 앱 스킴을 그대로 쓰지만, 문자 앱은 커스텀 스킴을 링크로 렌더링하지 않아 LMS는 Airbridge 단축링크로 변환해야 함
발송 채널알림 유형형식
앱 푸시채팅ohouseapp://ohou.se/customer_center?chat_id={채팅 ID}
앱 푸시1:1 문의ohouseapp://ohou.se/customer_center/inquiry/{문의 ID}
LMS공통https://link.ohou.se/{코드}?deeplink_url={URL 인코딩한 위 딥링크}
  • LMS용 Airbridge 단축링크 코드는 미발급 상태
  • 채팅 딥링크의 chat_id 분기 처리는 AICX 측 개발 범위

로깅 요구사항

  • 발송 건별로 아래 값을 남겨야 커버리지와 채널 비중을 사후에 측정할 수 있음
    • 회원번호, 알림 유형, 판정 결과(2단계 1~5번 중 어느 조건에 걸렸는지), 선택된 채널, 발송 요청 ID, 호출 시각

예외 처리와 잔여 오차

예외 처리

상황처리
회원번호 없음 — 비회원발송 없음. 조회 API 호출도 하지 않음
조회 API 실패 또는 타임아웃앱 푸시를 시도하고 실패 로그를 남기는 방향을 권고 (LMS 폴백은 중복 발송·비용 발생 위험)

사전 판정으로도 걸러지지 않는 케이스

분기 구조를 넣어도 아래 두 케이스는 해소되지 않는 잔여 오차임. 테스트 중 발송 가능으로 판정됐는데 단말에 안 뜨는 경우 이 둘 중 하나일 가능성이 높음

  • 무효 토큰 잔존 — Braze 푸시 토큰은 기기와 앱 설치 단위로 등록되고 로그아웃해도 이전 프로필에서 삭제되지 않음. 과거 로그인 이력만 있어도 토큰이 남아 판정을 통과하지만 단말에는 표시되지 않음
  • 계정 전환 후 미도달 — 앱이 로그인 시점에 Braze changeUser를 호출하지 않아, 앱을 완전히 재실행하기 전까지 어느 계정으로도 푸시가 도달하지 않음 (81분 실측, 상한 미확인). 근본 해결은 앱 측 작업이며 별도 협의 중

검증 역할 분담

  • AICX는 사내망 밖이라 QA 빌드 설치가 불가해 테스트용 단말 토큰을 만들 수 없음
