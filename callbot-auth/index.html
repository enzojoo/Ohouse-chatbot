개요

  • AI 콜봇은 8/19(화) 운영 배포를 목표로 하며, QA는 8/3~8/14 진행 중
  • 인입 경로는 대표번호 IVR 기준 1번(상품 및 주문 관련 문의)만 콜봇 선응대이며, 2번(시공/이사/제품설치/서비스)과 3번(기타)은 상담원으로 바로 연결됨
  • 콜봇은 전화 채널이라 고객 로그인 절차가 없어, 인앱 채팅(오늘의집 로그인 세션)과 인증 구조가 다름
    • 구) 채팅 채널인 카카오톡 챗봇(SMS 점유인증)과 유사한 편
    • 고객의 발신번호로 회원(userId)을 식별하고, 개인정보 조회가 필요한 시점에만 고객이 말한 성함을 대조하는 방식으로 확인하는 형태

    • 문자 추가 전송 후에도 미수신(최대 2회까지 전송 처리) — 딥링크 전달 불가
    • 고객의 상담원 연결 요청 — 본인확인 전후 무관하게 언제든 가능
본인확인은 플로우 진입 시점이 아니라 개인정보 조회가 필요해진 지점에서만 걸리므로, 일반 문의 구간은 비회원·다계정 고객도 동일하게 응대

현황

1. 시스템 인증 구조의 한계

  • 전화 채널이라 사용자 고유의 인증 토큰을 확보할 수 없음
    • 인앱/웹 채팅의 경우 로그인을 통해 고유의 회원정보와 인증을 확보하는 구조임
  • 따라서 발신번호로 회원을 조회해 userId를 확보한 뒤, AICX 서버가 오늘의집 조회 API를 호출하는 형태로 운영됨
    • 인증 방식은 기존 챗봇 API 인증 경로를 그대로 재사용, 전화번호를 바탕으로 userId를 확보하는 개념
    • 완벽한 1:1 인증 방식이 아니기 때문에 이번 배포는 조회용 API만 사용함
    • 쓰기(주문 취소, 클레임 접수 등) API는 허용되지 않아 고객 문자 발송으로 대체함
    • 현 인증 경로는 임시 적용이며, 콜봇 기능 확대를 위한 장기 인증 구조는 별도 논의 중

3. 본인확인 방식

  • 기본적인 정보(FAQ 또는 KMS 정보 기반)의 상담은 별도의 본인 확인 절차 없이 콜봇과 상담이 가능함
  • 다만 조회가 필요한 경우 발신번호의 userId에 등록된 이름에 대해 정보 확인 절차를 가져감
    • 콜봇이 이름을 먼저 말하지 않고, 고객이 말한 성함을 발신번호 기준 회원정보와 대조하는 방식으로 정보 확인
    • 콜봇이 조회된 이름을 먼저 부르는 방식은 번호 변경·양도·가족 발신 시 성명이 선노출되고, 세부 상담 없이 번호에 매핑된 이름만 취득하는 악용이 가능해 제외 처리
    • 콜봇 최초 연결 시 일괄 확인이 아니라 개인정보 조회가 필요한 시점에만 확인
※ 전화번호에 등록된 userId가 1개인 경우(1:1 매칭)에만 본인 확인 후 상담을 진행 / 비회원 또는 다계정인 경우 상담원 연결 처리

케이스별 시나리오

아래 시나리오는 API로 콜봇 자동화 처리가 가능하다는 전제로 작성되었으며, 인증에 따른 보안 검토 후 처리 방식은 변경될 수 있음

변경된 부분

  • 콜봇은 발신번호를 통해 회원번호(userId)를 조회하고, 이름 확인 후 주문 조회·포인트·쿠폰 목록 확인 등 Read 액션을 수행함
  • 이외 Write가 필요한 주문취소·클레임 접수 등은 LMS 문자 전송을 통해 고객 셀프 서비스로 처리함
    • 인앱·웹처럼 회원 본인인증을 거치는 구조가 아니라 연락처 기반 점유인증 개념이므로, 회원번호가 1개로 특정되더라도 통화를 건 사람이 해당 계정의 소유주임을 보증할 수 없음
    • 따라서 Write 액션은 고객이 앱에서 로그인한 뒤 직접 처리하도록 문자 발송 방식으로 구현하기로 결정함

공통 처리 원칙

  • 주문 관련 업무는 고객 및 대상 주문·상품을 확인한 후 진행함
  • 처리 전 대상 상품, 요청 내용, 주요 유의사항을 고객에게 다시 확인함
  • 주문 변경·취소처럼 상태를 바꾸는 업무는 번호 선택(DTMF) 최종 확인으로 고객의 명시적 동의를 받은 뒤 실행함
  • API 응답 또는 후속 상태 재조회로 결과가 확인된 경우에만 완료로 안내함
  • 확인 수단이 없거나 완료 상태가 확인되지 않으면 완료로 단정하지 않고 후속 절차를 안내함
  • 음성으로 처리하기 어렵거나 별도 화면이 필요한 업무는 SMS 링크로 안내함

처리 방식 비교 — 원안 대비 변경

원래 시나리오는 클레임 API로 콜봇이 직접 처리하는 것을 전제로 작성됐음. 콜봇 인증이 발신번호 기반 점유인증으로 결정되면서 Write 액션만 LMS 문자 셀프서비스로 전환됐고, Read 액션과 원래부터 딥링크였던 항목은 변동 없음

기능원래 계획현재 처리 방식구분

정리하면 실제로 바뀐 건 4개임 — 구매확정, 배송지 변경, 배송일 변경, 주문취소

  • 4개 모두 주문 상태를 바꾸는 Write 액션이며, 원래는 콜봇이 API로 실행하고 결과를 재조회해 완료를 안내하는 흐름이었음
  • 현재는 콜봇이 대상 주문까지만 특정해서 문자를 보내고, 실행과 완료 확인은 고객이 앱에서 수행함
  • 따라서 원안에 있던 번호 선택(DTMF) 최종 확인, API 실행 결과 판정, 완료 단정 금지 분기는 이 4개에서 동작하지 않음. 위 케이스별 다이어그램에 남아 있는 해당 구간은 보안 검토 후 API 처리가 허용될 때 적용되는 흐름임
  • 조회성 3개(주문·배송, 포인트, 쿠폰)는 콜봇이 음성으로 답하는 것이 원칙이며, 고객이 전체 목록을 보고 싶다고 하면 별도로 화면 링크(LMS 205 · 206 · 207)를 발송함
